# Relational schema: integration contract

Prepared 2 November 2026. Schema/validation owner: Taimoor. Mason owns the data-access functions, seed data and application quickstart; Shahmeer owns the UI/business layer. This document fixes the schema interface they can implement against.

## Files and runtime

- `src/dal/sql/schema.sql`: canonical DDL, twelve STRICT tables, thirteen foreign keys and four dimension-integrity triggers.
- `src/dal/schema_validation.py`: transaction-level rules and context helpers. This is a shared model-validation utility, not a replacement for Mason's database connection or CRUD modules.
- `scripts/create_schema.py`: non-destructive schema-only initializer. It refuses an existing database file. Mason can call this from the eventual quickstart.
- `tests/test_relational_schema.py`: synthetic behavioral tests, not the team's demo data.

Use Python 3.10+ with SQLite 3.37.0+. STRICT tables prevent nonconvertible values being stored in numeric columns. Check the SQLite library actually linked to Python with:

```sh
python -c "import sqlite3; print(sqlite3.sqlite_version)"
python scripts/create_schema.py --database data/etf_allocations.sqlite3
python -m unittest discover -s tests -v
```

Run commands from the repository root. The initializer creates empty tables only; it is not the full application quickstart. Do not execute schema.sql against an existing database to migrate it, and do not remove an existing database as an automatic recovery action.

## Connection and transaction boundary

Enable `PRAGMA foreign_keys = ON` on **every** connection, before any transaction. Application writes must use the model-validation boundary below. The UI calls business/data-access functions; it should not open its own connections or construct SQL.

```python
import sqlite3
from pathlib import Path
from dal.schema_validation import validated_transaction

project_root = Path(__file__).resolve().parents[2]  # adjust for the module's location
connection = sqlite3.connect(project_root / 'data/etf_allocations.sqlite3', isolation_level=None)
connection.execute('PRAGMA foreign_keys = ON')

with validated_transaction(connection, capture_root=project_root):
    # Parameterized INSERT/UPDATE/DELETE statements for ONE user operation.
    # Example: create the snapshot and all its entries together.
    pass
```

The app entry point must make `src` importable, for example by placing `main.py` under `src`. The example assumes that import setup. Database functions may accept the caller's connection or own a transaction, but should not nest transaction wrappers or commit inside the block. Let errors propagate out of the block; translate them into user-facing messages after rollback.

The wrapper validates the **whole proposed database state** before COMMIT. It rejects ETFs without identifiers, snapshots without entries, bad complete totals, incompatible category contexts, and missing/out-of-root captured files when capture_root is supplied. SQL constraints/triggers enforce types, required fields, business uniqueness, references, fraction ranges, allowed values, dates and matching dimensions.

These parent-side minimums/context/totals/file checks are application-level transaction rules. Direct SQL followed by a raw COMMIT can bypass them. This is an explicit limitation, not a claim that SQLite implements deferred assertions. For an external seed/import, finish all related rows in one validated transaction or run `validate_database` before committing. `executescript` implicitly changes transaction boundaries and must not be used inside the wrapper; use parameterized execute/executemany for the seed/import instead.

## Field conventions

- Every table has an autogenerated integer `Id`. Omit Id on normal INSERTs and use `cursor.lastrowid`. SQLite INTEGER PRIMARY KEY supplies it; AUTOINCREMENT is intentionally unnecessary. IDs may be reused after deletion and are not external business identifiers.
- All conceptual names use PascalCase. A many-to-one relationship becomes the FK column `<TargetEntity>Id`. FKs use `ON UPDATE RESTRICT ON DELETE RESTRICT` to prevent silent removal or reassignment of referenced identities. Delete dependent records explicitly inside one validated operation if a whole disclosure is intentionally removed.
- Required columns reject NULL; required text rejects empty/space-only values. Identity text is stored without surrounding ASCII spaces. Strip input before writing. Descriptive optional fields also reject empty strings: use NULL for unknown values.
- Names and email are descriptive and not unique. CustomerNumber is the single bank's existing customer reference. PortfolioReference is scoped by CustomerId. Provider registration is scoped by its issuing registry/jurisdiction.
- Identity text comparisons are case-sensitive (SQLite BINARY). IdentifierValue and ExchangeContext are uppercase. Do not assume that different capitalization of provider/scheme names means a different real organization; normalize consistently when loading data.
- `IdentifierScheme`: exactly `ISIN` or `Ticker`. ISIN has a 12-character uppercase format with two initial letters and a final digit; ExchangeContext must be NULL. The schema checks format, not the ISIN checksum or registry assignment. Ticker requires an uppercase, nonempty exchange context, such as `XTSX`.
- `DimensionName`: exactly `Sector` or `Geography`. `CoverageStatus`: exactly `Complete`, `Partial` or `Unknown`.
- Currency fields have three uppercase letters; DomicileCountryCode has two uppercase letters. These checks validate the stored format, not membership in an external code registry.
- Dates: `YYYY-MM-DD`, valid calendar dates. AllocationAsOfDate and HoldingAsOfDate are separate observations and are not automatically synchronized.
- RetrievedAt and optional PublishedAt: canonical UTC `YYYY-MM-DDTHH:MM:SS.ffffffZ`, always six fractional digits. Example: `2026-11-02T13:45:00.000000Z`. Convert a known timestamp using `datetime.astimezone(timezone.utc).strftime('%Y-%m-%dT%H:%M:%S.%fZ')`. When publication time is unknown, store PublishedAt = NULL; do not invent midnight or a timezone.
- Weights: numeric fractions in [0,1]. Convert UI percentages explicitly: 30% is stored as 0.30. Complete snapshot totals must be within 0.005 of 1, inclusive (0.5 percentage points); this configurable prototype tolerance was retained provisionally in [Taimoor's design evaluation](taimoor_design_evaluation.md) on 3 November and is not yet calibrated from genuine source precision. Partial/Unknown snapshots and sampled portfolio holdings are not required to sum to 1. Rows with zero weight are permitted.
- Url and CapturedFileRef are nonempty recorded values. The database does not retrieve URLs or verify their contents. CapturedFileRef is a project-relative path to a retained capture; use capture_root validation to check it exists within the repository. Source URL plus canonical retrieval time identifies the capture.
- A SourceLocator identifies one dated allocation block, including the relevant fund/date/row when a document contains multiple blocks. Distinct allocation bases at the same reporting date require distinct locators. Changing a source capture identity or locator may require updating disclosure-local ContextKeys in the same transaction.

## Construct ContextKey with the supplied functions

Do not hand-build ContextKey or use a shared value such as `Unknown` for unresolved classifications.

```python
from dal.schema_validation import scheme_context, disclosure_context

known_context = scheme_context('Synthetic Authority', 'Synthetic Sector', 'v1')
local_context = disclosure_context(
    'https://example.invalid/factsheet.pdf',
    '2026-11-02T13:45:00.000000Z',
    'page 2 / geography / fund A / 2026-10-31',
    'Geography',
)
```

These produce deterministic JSON tuple strings prefixed `scheme:` or `source:`. The example values are synthetic. Use a scheme context only when ClassificationSchemeId references a known Version and the authority/name/version is supported by the dataset's evidence. If the scheme or edition is unresolved, use a disclosure-local context based on URL, capture time, locator and dimension, even when an unknown-version ClassificationScheme row is linked. The validator checks ContextKey for every used category.

An unreferenced category has no disclosure from which to validate its local context; complete that linkage before relying on its meaning. A known-version scheme record and matching token do not independently verify the underlying classification claim. Matching labels or codes across different contexts never prove semantic equivalence.

## Seed/import order

Create Customer, ETFProvider, AllocationDimension and any ClassificationScheme records first. Then create Portfolio; ETF with its identifiers; Holding; SourceDocument; AllocationCategory; AllocationSnapshot with its entries. Use one transaction if some parents do not yet have their required children. NULL ClassificationSchemeId is valid. Preserve unknown versions as NULL.

All test fixtures are deliberately fictional. They prove constraint behavior and are not an adequate substitute for Mason's demonstration data or sourced ETF evidence. Real-source observations must match the retained capture; label synthetic bank/provider/ETF/observation records clearly.

## Proposed data-access operation outputs

These are suggested shared contracts, not implemented CRUD functions. Mason and Shahmeer can adjust names without changing the agreed columns.

| Operation | Inputs | Required output/behavior |
| --- | --- | --- |
| Search disclosures | ETFId, optional allocation date, optional AllocationDimensionId | SnapshotId, ETF name/identifier, allocation date, dimension, coverage, source identity; retain separate rows for different captures/blocks |
| Disclosure detail | AllocationSnapshotId | Snapshot and source fields; each entry's Id, category Id/Label/Code/ContextKey, optional scheme authority/name/version and WeightFraction |
| Portfolio view | PortfolioId and explicit holding date | Dated holdings with ETF identity; any disclosure date remains separate and visible; do not duplicate a holding by joining every historical snapshot |
| Create disclosure | Valid snapshot fields plus category/weight entries | New Id after validated COMMIT; snapshot and children saved together |
| Update entry | AllocationEntryId and new weight, or a coherent batch of entry changes | Validated transaction; preserve complete total within tolerance or explicitly correct CoverageStatus based on evidence |
| Delete entry | AllocationEntryId | Validated transaction; a complete disclosure's remaining total must remain valid and every saved disclosure must retain an entry |

An edit to one weight in a Complete disclosure may require adjusting another weight in the same operation. Do not silently change Complete to Partial merely to pass validation. For the simple single-entry edit/delete demo, use a genuinely Partial or Unknown example where appropriate, or provide a batch edit/whole-disclosure operation.

## Schema change procedure

The 3 November local review keeps the schema and all table/column names unchanged.
`search_disclosures` adds keyword-only `etf_id` and `allocation_dimension_id`,
and returns source identity/locator and representative ticker exchange.
Disclosure details now include the publisher and optional scheme metadata.
`get_customer_portfolio` accepts keyword-only `portfolio_id` and
`holding_as_of_date`. Customer-only calls work when there is one unambiguous
portfolio/date; multiple choices require explicit input or raise `ValidationError`.
Batch edits reject missing IDs before commit. Quickstart reuses existing data;
`--reset` explicitly replaces it after a successful rebuild. The in-memory query
demo uses the validated Python seed loader. See [the evaluation](taimoor_evaluation.md).

Treat these table/column names as the initial implementation contract. Discuss changes with both teammates before renaming them, update schema/dictionary/report fragments together, and rerun the behavioral tests. No database migration or existing application is supplied by this contribution.
