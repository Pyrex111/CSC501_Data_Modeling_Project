## How to understand and review the design

1. **Internal key versus business identity.** Customer.Id is generated by our database. CustomerNumber is the existing bank reference. A provider's identity is its registration number within an issuing registry; a name alone does not prove uniqueness. The schema preserves both technical record identity and documented business rules.
2. **Relationships become FK columns.** Portfolio.CustomerId implements Owns; AllocationEntry.AllocationSnapshotId and AllocationCategoryId implement its two associations. These added SQL columns are the relational mapping, not extra conceptual attributes. Holding and AllocationEntry already carry association facts such as weight/date.
3. **Identity needs scope.** A ticker requires an exchange. A category label requires a dimension/context. A source URL requires its retrieval time to identify a capture. An unknown classification edition stays unknown.
4. **SQL checks and transaction checks serve different rules.** SQL protects references, mandatory fields, uniqueness, fractions and matching dimensions. A validated transaction checks the whole proposed saved state, including that a snapshot has entries, an ETF has identifiers and a Complete disclosure has a plausible total. Deleting or editing records can therefore fail even if an individual SQL statement looks valid.
5. **Evidence and observation dates are distinct.** HoldingAsOfDate describes the customer's position; AllocationAsOfDate describes the provider's allocation; RetrievedAt describes the retained source capture. None should silently replace another.
