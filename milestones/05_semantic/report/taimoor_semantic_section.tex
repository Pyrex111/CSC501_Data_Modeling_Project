\subsection{Graph population, SPARQL, and reproducibility}
We implemented an embedded Oxigraph backend through a pinned PyOxigraph package,
with a persistent local store and RDF/XML import/export~\cite{oxigraphStore,oxigraphIO}.
The accepted, fully synthetic relational dataset populates twelve entity classes
and 356 instance triples. Each record receives a stable project IRI within the
demonstration dataset. Relationships become IRI edges, scalar values become typed
literals, and unknown optional values are omitted. Holding and allocation dates,
classification context, coverage and source provenance remain explicit.
The term and resource-identity contract matches Mason's version 1.1.0 ontology,
loaded into a separate named graph. Loading axioms does not enable OWL reasoning.

Six standalone SPARQL SELECT queries translate the accepted SQL analyses.
We compared complete result multisets, including duplicate multiplicity and
unbound optional values, rather than comparing row counts alone. All six matched,
with 8, 2, 5, 5, 5 and 17 result rows. Numeric comparisons allow binary-floating
differences at ten decimal places. The portfolio query remains a diagnostic
candidate listing; it does not establish compatible observation dates or a
validated portfolio exposure total.

The graph data-access layer supplies search, disclosure details, dated portfolios,
form lookups and SPARQL-backed creation, editing and deletion~\cite{sparqlUpdate}.
An operation first changes a candidate graph. Validation precedes publication of
the exact delta in one transactional update, so rejected edits preserve the live
graph. Application writers share a process lock. A temporary checker projects
candidate records into the accepted relational constraints. Startup also binds
Mason's native graph validator, including retained-file checks, to every proposed
write. Both checks run before publication; native-only rejection tests isolate
the graph validator by bypassing the relational checker within those tests.

The semantic quickstart builds or reuses its own store, exports RDF/XML and can
rerun all SQL/SPARQL comparisons without altering the accepted application database.
Integration verification passed 160 tests: 74 existing tests, 26 backend tests,
51 ontology/validation tests and nine runtime integration tests.
It includes RDF round-tripping, persistence, result compatibility, invalid-weight
and context rejection, coherent batch changes and unchanged-state checks after
rejected writes. The graph-backed application and its UI evidence remain pending.
